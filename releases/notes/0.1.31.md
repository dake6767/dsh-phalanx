# 0.1.31

## English

### Plugin library: one input for npm and GitHub

**Add plugin** now takes one plugin reference instead of separate name and version
fields. Accepted inputs are a package name, `package@1.2.3`, `package@latest`, a
scoped name such as `@scope/package`, `github:owner/repo`, and a
`https://github.com/owner/repo` address. Version ranges, other tags and any other
Git host are rejected with their own messages. Precheck resolves a bare name or
`@latest` to an exact version and pins a GitHub default branch to its latest
commit, so a stored plugin never drifts afterward.

A plugin keeps the source recorded when it was added: npm, an uploaded archive or a
particular GitHub repository. The same package name cannot come from two sources;
adding from another source is refused until the plugin is removed. Updates reuse
the original source: npm compares the stored version with `latest`, and a GitHub
source compares its pinned commit with the default branch HEAD, so a new commit is
reported even when the package version did not change. Updates are checked only
when requested and still go through precheck and explicit confirmation.

GitHub sources are packed in a disposable network-disabled container without
running repository scripts, then checked like an upload. The platform does not
build plugins: a repository missing the files its `main`, `exports` or
`dsh.bundle` entries declare is refused with a build-required explanation, so use
its npm package or upload a `.tgz`. Dependencies must come from the npm registry.
The plugin card wording for a missing access configuration now says that upstream
and access settings are not configured; it does not describe the installation
state.

### Skill import and skill packs

Discovery validates each skill independently. A skill whose `SKILL.md` YAML
frontmatter is invalid is listed under **Unable to import** with its file path,
the failing field and the reason, while valid skills from the same source can
still be imported in one preview. Source-level problems such as unsafe paths,
links or special files still reject the whole source.

A skill pack appears as one expandable row in the skill library, group grants,
expert settings and member skill selection. Packed skills stay inside their pack
instead of occupying a second top-level row, unless a direct grant or member
selection also keeps them visible; a member who cannot see any parent pack
retains the individual entry that was already available. Expanding a visible pack
shows its children, and granting or selecting the whole pack still makes every
available child usable. Existing grants and selections are preserved.

### Shared models: per-supplier groups and three protocols

Each enabled shared model supplier is now its own model group in DSH, titled with
the supplier name; entries show only the model name, and the fixed English
"Shared models" title is gone. Entering DSH synchronizes that browser's platform
language for the "shared models not configured" explanation; an account keeps the
language of its most recent entry. Disabled or deleted suppliers and models do not
appear.

Supplier configuration now includes a protocol: **Anthropic Messages**, **OpenAI
Chat Completions** or **OpenAI Responses**. The Base URL hint follows the selected
protocol and names the endpoint the gateway appends. One supplier uses one
protocol; configure the same upstream twice to use two protocols. The gateway
accepts the corresponding member path and authentication shape, forwards the
request in the same protocol to the supplier endpoint with the supplier's key,
replacing only the model identity with the supplier's model name, and never
converts between protocols. Requests to a supplier whose protocol does not match
the request are refused. Model usage records input, output, cache read and cache
write tokens for all three protocols; counters the upstream does not report stay
unknown instead of being filled with zero. Input is recorded without cache
tokens; for the OpenAI protocols a missing cache counter also leaves the derived
input unknown.

### Debian-family host support (included from 0.1.30)

This release also publishes the Debian-family host support prepared for 0.1.30:
the installer accepts Debian-family amd64 hosts by distribution family and host
capabilities, with Ubuntu 24.04 and 26.04 on the verified list, capability
diagnostics for Podman, passt, systemd, cgroup v2 and rootless Podman, and the
newer pasta loopback forwarding. Non-Debian hosts are refused before host
changes. See the [0.1.30 notes](0.1.30.md) for the full description and one-time
verification record.

### Upgrade notes

The supported DSH runtime remains `dsh-v0.2.1-rc.5`. Installations upgraded from
an earlier release keep member accounts, member files and other platform data.
Plugins added before this release do not carry a source record and are removed
with their grants, member selections, plugin settings and expert references on
upgrade; re-add and reconfigure them and review experts that referenced them after
entering the management interface. There is no automatic migration of old plugin
sources.

## 简体中文

### 插件库：一个输入框，npm 与 GitHub

「添加插件」改为一个插件标识输入框，不再分成包名和版本两个字段。接受包名、
`package@1.2.3`、`package@latest`、`@scope/package` 等带 scope 的名称、
`github:owner/repo` 和 `https://github.com/owner/repo` 地址。版本范围、其他标签
和其他 Git 主机分别给出明确拒绝。预检把省略版本或 `@latest` 解析为精确版本，
把 GitHub 默认分支固定到最新提交，入库后版本不再漂移。

插件保留添加时记录的来源：npm、上传的归档或某个 GitHub 仓库。同一包名不能来自
两个来源；从另一来源添加会被拒绝，需先移除该插件。更新沿用原来源：npm 插件比较
库内版本与 `latest`，GitHub 插件比较记录的提交与默认分支最新提交，因此包版本号
未变时新提交也会提示。更新只在管理员按需检查时触发，仍需预检并明确确认。

GitHub 来源在一次性断网容器中打包，不执行仓库脚本，之后与上传包走相同检查。
平台不构建插件：仓库缺少 `main`、`exports` 或 `dsh.bundle` 声明的文件时以「需要
构建」说明拒绝，请改用其 npm 包或上传 `.tgz`。依赖必须来自 npm registry。插件
卡片上「接入未配置」的措辞改为说明尚未配置上游与接入设置，不再让管理员误读为
安装状态。

### 技能导入与技能包

发现阶段逐个校验技能。`SKILL.md` 的 YAML frontmatter 无效时，该技能列入
「无法导入」，显示文件路径、出错字段和原因；同一来源中合法的技能仍可在这次
预览中导入。不安全路径、链接或特殊文件等仓库级问题仍整批拒绝。

技能包在技能库、分组授权、专家设置和成员技能选择中占一行并可展开。包内技能
不再在顶层单独占行，除非另有直接授权或成员自选使其保持可见；成员看不到任何
父包时，原本已可用的该技能仍保留单独入口。展开可见的包会显示其子技能；对整包
授权或自选仍使全部可用子技能生效。已有授权与选择保持不变。

### 共享模型：按供应商分组与三种协议

每个启用的共享模型供应商在 DSH 中成为独立分组，标题为供应商名；条目只显示
模型名，固定英文「Shared models」标题不再出现。进入 DSH 时同步该浏览器的平台
语言，用于「共享模型未配置」说明；同一账号以最近一次进入的语言为准。停用的
供应商和模型不出现。

供应商配置新增协议：**Anthropic Messages**、**OpenAI Chat Completions** 或
**OpenAI Responses**。Base URL 提示随协议变化并说明网关追加的端点。一个供应商
只用一种协议；同一上游需要两种协议时配置两个供应商。网关接受对应的成员路径与
鉴权方式，按同一协议转发到供应商端点并注入供应商密钥，只把模型标识替换为供应商的
模型名，不做协议互转；请求协议与供应商协议不一致时拒绝。三种协议的输入、输出、缓存读和缓存写 token 都进入用量记录；
上游未报告的计数保持「未知」，不补零。输入按不含缓存 token 的口径记录；OpenAI 两种协议在缓存计数缺失时
派生输入也记未知。

### Debian 系主机支持（随本版发布 0.1.30 内容）

本版一并发布为 0.1.30 准备的 Debian 系主机支持：安装器按发行版系列和主机能力
接受 Debian 系 amd64 主机，已验证名单包含 Ubuntu 24.04 与 26.04；对 Podman、
passt、systemd、cgroup v2 和 rootless Podman 给出能力诊断；新版 pasta 使用新的
loopback 转发。非 Debian 系主机在修改主机前被拒绝。完整说明与一次性验证记录见
[0.1.30 发布说明](0.1.30.md)。

### 升级说明

支持的 DSH 运行时仍为 `dsh-v0.2.1-rc.5`。从更早版本升级会保留成员账户、成员文件
和其他平台数据。本版之前添加的插件没有来源记录，升级时会连同其分组授权、成员
自选、插件设置和专家引用一起移除；进入管理界面后重新添加并配置插件，并复核引用过
它们的专家配置。平台不自动迁移旧插件
来源。
